# 2026.269.1910 — test(require): lock the manifest-is-the-declaration contract

## Summary

`plugin-example-require` is the reference fixture for charly's **declared inter-plugin
dependency** mechanism (`plugin.requires:`). Its candy manifest declares TWO peers — one
compiled into charly (`verb:externalprobe`; the resolve branch) and one served
out-of-process (`verb:exampledispatchpeer`; the on-demand connect branch) — and its
`examplerequire` verb peer-invokes both over the host broker
(`sdk.Executor.InvokeProvider`). The authored manifest is THE source of the declaration:
there is no `sdk.NewMetaWithRequires` call anywhere, so a plugin author declares a peer
ONCE and neither charly core nor another plugin's Go changes.

The fixture body (candy manifest + Go module + `cmd/serve` shim + CI + README) was
bootstrapped onto `main` by the org's sanctioned `bootstrap-repo-main` workflow — the org
main-protection ruleset's `creation` rule blocks creating a brand-new repo's first `main`
by every operator path (`git push`, the contents API, repo auto_init), and its only bypass
actor is the `charly-auto-merge` App that workflow mints. This PR is the normal PR-only
landing on top of that bootstrap and drives the tag-on-merge release the charly module pin
needs. (The operator explicitly chose a NEW standalone repo for this fixture — see the A6
design decision — which is why the tag does not exist yet: this merge produces it.)

This diff has two changes, both surfaced/required by the live run:

1. **`candy/plugin-example-require/charly.yml` — the fixture's ADE plan** now dispatches
   `verb:examplerequire` with both declared peer words, so its acceptance test exercises
   declare → gate-resolve → peer-invoke at runtime (and its word is referenced by the
   project's plan, so any load of a project containing this candy drives the gate).
2. **`candy/plugin-example-require/plugin.go` — the verb returns a check-result
   envelope** (`{"status":"pass","message":…,"builtin_peer":…,"external_peer":…}`). The
   host's `pluginCheckResult` decode defaults an **absent** `status` to FAIL, which the
   live run caught: the verb dispatched and peer-invoked both peers, but the step failed
   for want of a `status` field.
